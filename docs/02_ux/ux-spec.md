# Wallet Exchange — UX Specification

**Статус:** CHAT-03 BASELINE  
**Дата:** 2026-08-05  
**Владелец:** CHAT-03 UX/UI  
**Интерактивная реализация:** [`../../prototype/`](../../prototype/)

<a id="ux-01"></a>
## 1. Цель и scope

Спецификация определяет русскоязычный desktop/mobile-интерфейс концептуального модуля обмена RUB/USDT и его клиентское демонстрационное поведение от открытия формы до `completed` или `rejected`.

В scope входят две пары, курс CoinGecko, исходная сумма, авторасчёт, общий/зарезервированный/доступный баланс, повторная проверка условий, обычное и изменённое подтверждение, sync-успех, воспроизводимый async, резерв, terminal-результаты, ошибки, история и идемпотентный повтор.

Регистрация, KYC/AML, пополнение/вывод, карты, переводы, глобальная финансовая история, админка, комиссии, спред, отмена, уведомления, поддержка, backend и production-инфраструктура не проектируются.

**Трассировка:** `BR-001`–`BR-004`, `CON-001`–`CON-010`, `ART-002`, `ART-003`.

<a id="ux-03"></a>
## 3. Роль и основной пользовательский поток

Единственная роль — пользователь демонстрационного кошелька.

1. Пользователь открывает форму и видит два валютных баланса.
2. Приложение получает котировку Tether/RUB из CoinGecko.
3. Пользователь выбирает RUB → USDT или USDT → RUB.
4. Пользователь вводит только исходную целую сумму либо выбирает «Обменять всё».
5. Результат пересчитывается автоматически и отображается с одним знаком.
6. Приложение валидирует формат, минимум и доступный баланс.
7. По действию «Проверить условия» блокируется повторная отправка.
8. Приложение повторно получает курс и проверяет доступный баланс.
9. Неизменившийся результат ведёт к обычному подтверждению.
10. Изменившийся округлённый результат ведёт к отдельному согласию без второго окна.
11. Sync-операция завершается `completed`.
12. Demo-async создаёт `pending` с резервом и затем явно завершается `completed` или `rejected`.
13. Результат, балансы и локальная история обновляются согласованно.

**Трассировка:** `UR-001`–`UR-013`, `FR-004`–`FR-029`, `VAL-001`–`VAL-015`.

<a id="ux-04"></a>
## 4. Информационная архитектура

Основной экран состоит из пяти зон:

1. шапка функции и сброс тестовых данных;
2. сводка кошелька и две карточки балансов;
3. карточка новой заявки с курсом, парой, вводом и результатом;
4. визуально отделённая demo-зона сценариев;
5. последняя заявка и локальная история.

Модальное окно используется только для подтверждения последних условий. Terminal- и pending-состояния показываются в основном потоке и доступны повторно через историю.

<a id="ux-05"></a>
## 5. Desktop-экран

Целевой основной viewport — Full HD 1920×1080. Контент ограничен шириной `1240 px`, чтобы сохранить деловую плотность и читаемость.

- верхняя сводка занимает полную ширину;
- RUB и USDT отображаются рядом;
- ниже форма занимает большую левую колонку;
- demo-панель занимает меньшую правую колонку;
- результат и история расположены полноширинно под основным потоком;
- критическое действие находится в нижней части формы и имеет максимальную визуальную заметность.

Репрезентативное состояние: [`screenshots/desktop-default.webp`](screenshots/desktop-default.webp).

<a id="ux-06"></a>
## 6. Mobile-экран

При ширине до `900 px` форма и demo-панель переходят в один столбец. При ширине до `640 px`:

- карточки балансов идут последовательно;
- выбор направления становится вертикальным;
- курс и метаданные располагаются друг под другом;
- result metrics переходят в один столбец;
- история становится карточной;
- кнопки модального окна занимают полную ширину;
- бизнес-действия и набор данных остаются теми же, что на desktop.

Репрезентативное состояние: [`screenshots/mobile-default.webp`](screenshots/mobile-default.webp).

<a id="ux-09"></a>
## 9. Валюты, числа и время

- используются только коды `RUB` и `USDT`;
- направление курса всегда: `1 USDT = X RUB`;
- исходный ввод отображается без дробной части;
- получаемая/фактическая сумма отображается с одним знаком;
- дробный разделитель — точка;
- большие числа временно группируются пробелом по `AS-001`, например `250 000.0`;
- `OQ-M-01` остаётся открытым для окончательного формата;
- время курса подписано «Обновлено …»;
- история использует локальный часовой пояс браузера по `AS-002`;
- `OQ-M-02` остаётся открытым; локальное время не объявляется окончательным требованием.

<a id="ux-10"></a>
## 10. Валидация

Порядок клиентских проверок:

1. поле не пустое;
2. формат состоит из целого числа;
3. значение больше нуля;
4. дробная часть отсутствует;
5. существует корректная котировка;
6. сумма не ниже минимума;
7. сумма не выше доступного баланса.

Минимум:

- RUB → USDT: `ceil(rate)` RUB, чтобы получить не менее `1.0 USDT`;
- USDT → RUB: `1 USDT`.

Ошибка показывается рядом с полем. Основная кнопка получает настоящий `disabled`. При повторной проверке недостаточного баланса модальное окно не показывается и заявка не создаётся.

**Трассировка:** `VAL-001`–`VAL-015`, `ERR-001`–`ERR-003`, `BRL-001`, `BRL-002`, `BRL-006`.

<a id="ux-11"></a>
## 11. Обычное подтверждение

Показывается только после свежей котировки и повторной проверки баланса, если округлённая получаемая сумма не изменилась.

Содержит:

- исходную сумму и валюту;
- получаемую сумму и валюту;
- курс `1 USDT = X RUB`;
- комиссию и спред `0`;
- ключ попытки для demo-наблюдаемости;
- последствия: sync-изменение двух балансов или async-резерв;
- отсутствие пользовательской отмены.

<a id="ux-12"></a>
## 12. Изменение курса и результата

Сравниваются значения target amount после одинакового округления до одного знака. Скрытое изменение курса без изменения отображаемого результата не создаёт лишнее согласие.

При изменении:

- заголовок становится «Результат изменился»;
- показываются прежний и новый результат;
- пользователь может вернуться или согласиться;
- после согласия заявка создаётся сразу;
- дополнительное обычное подтверждение не показывается.

Для воспроизводимой демонстрации demo-переключатель корректирует только свежую реальную котировку на `+1.5%` и явно маркирует quote ID как demo. Это не production-правило.

**Трассировка:** `FR-008`–`FR-012`, `BRL-008`, `ERR-006`, `UX-011`.

<a id="ux-13"></a>
## 13. `pending`, `completed`, `rejected`

### `pending`

Показываются статус дополнительной проверки, подтверждённые условия, размер резерва, актуальный доступный баланс, возможное изменение фактического результата и отсутствие отмены. Активный резерв существует только в этом статусе.

### `completed`

Показываются фактические исходная и полученная суммы и фактический курс. Для sync фактический курс равен подтверждённому. Для demo-async фактический курс может отличаться и показывается отдельно.

### `rejected`

Показывается, что обмен не выполнен, целевая валюта не зачислена, а существовавший резерв освобождён.

**Трассировка:** `FR-023`–`FR-028`, `FR-035`, `FR-036`, `BRL-011`–`BRL-017`, `UX-012`–`UX-015`.

<a id="ux-14"></a>
## 14. Ошибки

| Ошибка | Пользовательское сообщение / реакция | Финансовый эффект |
|---|---|---|
| empty/format/zero/fraction | локальное сообщение у поля | отсутствует |
| below minimum | минимум и эквивалент 1.0 USDT | отсутствует |
| insufficient balance | актуальный available | отсутствует |
| CoinGecko unavailable/invalid/timeout | «Не удалось получить корректный курс…» | заявка не создана |
| changed result | отдельное согласие, не terminal error | отсутствует до согласия |
| technical | общий текст и demo-код | заявка не создана |
| async rejection | `rejected`, резерв освобождён | target не зачислен |
| idempotent repeat | существующий результат | повторный эффект отсутствует |

Stack trace, внутренние URL, payload и детали компонентов пользователю не показываются.

<a id="ux-15"></a>
## 15. История заявок

История хранится в `localStorage` текущего браузера и содержит только заявки обмена этого модуля.

Минимальная запись показывает:

- ID заявки и operation key;
- дату/время;
- направление;
- исходную сумму;
- подтверждённую либо фактическую целевую сумму;
- статус;
- подтверждённый курс;
- фактический async-курс, если отличается;
- резерв для `pending`.

Выбор записи повторно открывает соответствующий result card. `created` поддержан визуально как допустимый статус модели, хотя нормальный клиентский поток не оставляет устойчивую запись в `created`.

<a id="ux-16"></a>
## 16. Доступность

- semantic `main`, `section`, `aside`, `form`, `fieldset`, `dialog`;
- skip link к форме;
- корректные `label`, `legend`, radio и select;
- клавиатурный доступ ко всем действиям;
- заметный `:focus-visible` контур;
- ошибки связаны с полем через `aria-describedby` и `aria-invalid`;
- динамические сообщения используют `aria-live`;
- блокировки используют атрибут `disabled`;
- состояния различаются текстом, пиктограммой/рамкой и цветом;
- предусмотрен `prefers-reduced-motion`;
- контраст текста и основных действий рассчитан на светлую тему.

<a id="ux-17"></a>
## 17. Адаптивное поведение

Breakpoint-логика:

- `> 900 px`: двухколоночная форма/demo;

Адаптив не скрывает бизнес-данные и не меняет правила обработки.

## 19. Demo-only элементы

В отдельной жёлто-нейтральной панели находятся:

- переключатель «Дополнительная проверка» (`DEC-036`);
- выбор `pending → completed/rejected`;

Каждый элемент текстом обозначен как демонстрационный. Специальная сумма, скрытый случайный триггер и production-объяснение не используются.

<a id="ux-22"></a>
## 22. Передача следующим этапам

### Gherkin
