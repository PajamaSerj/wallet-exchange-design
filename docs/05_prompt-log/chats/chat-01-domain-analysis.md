## Использованные промпты

### Основной пользовательский промпт

Пользователь назначил чат старшим бизнес- и системным аналитиком этапа 1, ограничил scope функциональностью создания заявки на обмен, задал приоритет источников, список файлов, запрет на преждевременное проектирование и перечень открытых вопросов с частью готовых ответов.

### Уточняющий ответ пользователя

Пользователь подтвердил:

- ответственность модуля до `completed` или `rejected`;
- ввод только исходной суммы;
- минимум как эквивалент 1.0 USDT;
- отображение `pending` и результата на экране и в истории;
- идентификатор котировки;
- сравнение фактически отображаемого результата при изменении курса;
- идемпотентность;
- минимальный набор данных заявки;
- каталог ошибок;
- `localStorage`;
- клиентскую симуляцию;
- выводы анализа частоты курса;
- использование публичных изображений внутреннего интерфейса Bidzaar и разрешение аналитически определить недостающие стили.

### Рабочие инструкции ИИ

1. Сопоставить бриф с governance-шаблонами.
2. Не считать `SCAFFOLD` готовым решением.
3. Отделить прямые требования брифа от решений пользователя и аналитических следствий.
4. Сначала закрыть `BLOCKER` и `HIGH`.
5. После ответов сформировать атомарный проверяемый реестр.
6. Сохранить только минимальные контракты внешних зависимостей.
7. Зафиксировать наблюдаемое визуальное направление отдельно от интерпретации.
8. Не создавать артефакты следующих этапов.

## Выполненные действия

1. Изучены обязательные файлы репозитория.
2. Подтверждено, что governance-файлы были каркасами `SCAFFOLD`, а checklist — baseline брифа.

6. Определены термины, сущности, связи, события и жизненный цикл.

## Обнаруженные ошибки, риски или возможные галлюцинации ИИ

| Проблема | Как обнаружена | Исправление |
|---|---|---|
| Раннее предложение сравнивать полное значение курса API | Пользователь выбрал сравнение фактически отображаемого результата | Запись заменена решением DEC-012; ранний вариант отмечен `SUPERSEDED` |
| Возможное смешение «создания заявки» с проектированием всей платформы | Проверка scope против явного ограничения пользователя | Все смежные системы сведены к минимальным контрактам; глобальная архитектура исключена |
| Риск трактовать внутренние изображения Bidzaar как точные дизайн-токены | Публичные изображения различаются, включая светлые и тёмные варианты | Зафиксированы только повторяющиеся признаки; размеры, цвета и тени обозначены как интерпретация |
| Риск считать `cancelled` допустимым статусом | Сопоставлены ответы о статусах и запрет пользовательской отмены | `cancelled` исключён; используется `rejected` |
| Набор H-04 не содержал фактический async-курс, хотя итог может изменяться | Проверка согласованности данных и поведения `pending` | Добавлены фактический курс и сумма для `completed`, не смешивая их с двумя пред-submit котировками |
| Риск воспринимать `localStorage` как полноценную историю пользователя | Сопоставление с ограничением демонстрационного scope | История явно ограничена текущим браузером и только заявками обмена |

## Ручные исправления и решения пользователя

- Выбран вариант B для границы ответственности.
- Выбран вариант A для направления ввода.
- Выбран вариант B для минимальной суммы.
- Выбран вариант C для отображения `pending`.
- Утверждены идентификатор котировки, идемпотентность, данные заявки, ошибки, `localStorage` и клиентская симуляция.
- Для Bidzaar снята необходимость запрашивать дополнительные скриншоты; разрешена осторожная интерпретация.
- Критерий изменения курса заменён с технического изменения значения на изменение пользовательского результата.

## Связанные требования

Все требования `BR-001`–`CON-010` в `docs/00_governance/requirements-register.md`.

Ключевые группы для передачи:

- SDD: `BR-*`, `FR-*`, `BRL-*`, `DR-*`, `VAL-*`, `ERR-*`, `NFR-*`, `CON-*`.
- UX/UI: `UR-*`, `FR-004`–`FR-012`, `FR-015`–`FR-018`, `FR-022`, `FR-025`–`FR-036`, `UX-*`, `ERR-*`.
- Gherkin: основной поток, недостаточный баланс, изменение курса, идемпотентность, `pending`, `rejected`, ошибки курса.
- OpenAPI: заявки, котировки, балансы, статусы, подтверждённые и фактические значения, идемпотентность, ошибки.
- Итоговый аудит: все требования и acceptance IDs из матрицы.
