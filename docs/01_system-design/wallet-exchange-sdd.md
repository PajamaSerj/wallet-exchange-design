# Wallet Exchange — High-Level System Design

**Статус:** BASELINE FOR DOWNSTREAM ARTIFACTS  
**Владелец:** CHAT-02 System Design  
**Дата:** 2026-08-05  
**Scope:** создание и доведение заявки RUB/USDT до `completed` или `rejected`

<a id="sdd-01"></a>
## 1. Назначение и контекст

Документ определяет высокоуровневое системное решение функции обмена валют во внутреннем модуле «Кошелёк пользователя». Решение должно быть достаточно определённым для последующей подготовки UX/UI-прототипа, Gherkin-сценариев, OpenAPI-спецификации, интеграционной проверки и итогового аудита, но не является детальным техническим проектом финтех-платформы.

Пользователь воспринимает обмен как одну операцию: выбирает направление, вводит исходную сумму, подтверждает последний показанный результат и получает терминальный результат `completed` либо `rejected`. Основной вариант выполняется синхронно; при необходимости допускается воспроизводимый переход на внешнюю дополнительную проверку со статусом `pending`.

Нормативные источники применяются в порядке приоритета:

1. `Wallet_Exchange_Project_Brief.md`;
2. согласованные пользователем решения этапа 1;
3. `docs/00_governance/assumptions-decisions.md`;
4. `docs/00_governance/requirements-register.md`;
5. остальные материалы репозитория.

Классификация положений документа:

- **прямое требование** — следует из брифа;
- **согласованное решение** — принято пользователем на этапе 1;
- **действующее допущение** — временное положение `AS-*`;
- **проектное решение этапа 2** — архитектурный выбор `DEC-036`–`DEC-040`;
- **открытый вопрос** — незакрытое положение `OQ-*`;
- **рекомендация** — передача следующему этапу без статуса пользовательского требования.

Документ является базовой линией для следующих артефактов. Окончательные REST-пути, имена API-полей, HTTP-коды, язык программирования, фреймворк, СУБД, облачная платформа и production-инфраструктура здесь не определяются.

**Связанные требования:** `BR-001`–`BR-004`, `ART-001`, `NFR-004`, `CON-001`, `CON-007`.

## 2. Scope / Out of Scope

### 2.1. Scope

В решение входят:

- направления RUB → USDT и USDT → RUB;
- загрузка и нормализация котировки Tether в RUB;
- предварительный расчёт получаемой суммы;
- проверка формата, минимума и доступного баланса;
- действие «Обменять всё» по доступному остатку;
- повторная проверка курса и баланса перед созданием заявки;
- обычное подтверждение либо согласие с изменившимся отображаемым результатом;
- создание не более одной заявки на одну пользовательскую попытку;
- синхронное завершение либо переход на внешнюю дополнительную проверку;
- резервирование исходной суммы только для `pending`;
- согласованное изменение двух валютных балансов;
- защита от повторного применения финансового результата;
- отображение `completed`, `pending` и `rejected`;
- локальная история демонстрационных заявок;
- ошибки и исключительные состояния.

### 2.2. Out of Scope

Не проектируются регистрация и авторизация, KYC/AML, пополнение и вывод, карты, переводы между пользователями, глобальная история финансовых операций, административная панель, инфраструктура биржи, собственный сервис рыночных данных, бухгалтерский или блокчейн-реестр, уведомления, поддержка, программа лояльности, пользовательская отмена, комиссии, спред, дополнительные дневные или пользовательские лимиты, глобальная архитектура платформы и production-инфраструктура.

### 2.3. Граница ответственности

Ответственность начинается при открытии формы обмена: модуль запрашивает котировку и актуальное состояние кошелька. Ответственность заканчивается только после:

- фиксации `completed` и согласованного изменения обоих валютных балансов; либо
- фиксации `rejected` без зачисления целевой валюты и, если существовал резерв, после его освобождения;
- обновления локального пользовательского представления истории.

`pending` не является точкой окончания ответственности. Пользовательская отмена не поддерживается.

**Связанные требования:** `CON-001`–`CON-010`, `FR-001`–`FR-003`, `FR-033`, `FR-034`, `BRL-003`, `BRL-004`, `BRL-013`, `BRL-014`.

## 4. Термины

| Термин | Определение |
|---|---|
| Заявка на обмен | бизнес-объект, фиксирующий намерение обменять исходную сумму на целевую и живущий до `completed` или `rejected` |
| Исходная валюта | валюта, средства которой пользователь отдаёт |
| Целевая валюта | валюта, средства которой пользователь получает |
| Исходная сумма | положительное целое количество исходной валюты, введённое пользователем |
| Получаемая сумма | рассчитанное количество целевой валюты, отображаемое с округлением до одного знака после точки |
| Курс | цена 1 USDT в RUB, полученная из согласованного источника |
| Котировка | идентифицированный снимок курса и времени обновления источника |
| Подтверждённые условия | последние показанные и явно принятые пользователем направление, исходная сумма, курс и получаемая сумма |
| Фактические условия | курс и полученная сумма, реально применённые при асинхронном `completed` |
| Общий баланс | полный остаток валюты до вычета активных резервов |
| Зарезервированная сумма | часть исходного остатка, связанная с активной заявкой `pending` |
| Доступный баланс | общий баланс минус активные резервы |
| Ключ операции | идентификатор одной пользовательской попытки подтверждения для идемпотентной обработки |
| Локальная история | представление заявок обмена в `localStorage` текущего браузера; не глобальная финансовая история |
| Терминальное состояние | `completed` или `rejected`; возврат в `created`/`pending` запрещён |

**Связанные требования:** `DR-001`–`DR-020`, `BRL-011`–`BRL-016`.

## 6. Основной пользовательский поток

1. Пользователь открывает форму обмена.
2. Модуль запрашивает предварительную котировку Tether в RUB.
3. Модуль получает и отображает общий, зарезервированный и доступный баланс RUB и USDT.
4. Пользователь выбирает RUB → USDT или USDT → RUB.
5. Пользователь вводит положительную целую исходную сумму либо применяет «Обменять всё», подставляющее доступный баланс.
6. Компонент расчёта автоматически вычисляет получаемую сумму и округляет отображение до одного знака после точки.
7. Выполняется предварительная валидация формата, минимума, пары, котировки и доступного баланса; при блокирующей ошибке отправка недоступна.
8. Пользователь инициирует отправку; для попытки создаётся уникальный ключ операции, повторное подтверждение в интерфейсе блокируется.
9. Модуль повторно запрашивает котировку и заново рассчитывает отображаемую получаемую сумму.
10. Модуль повторно получает баланс с логическим признаком актуальности и проверяет достаточность.
11. Если отображаемый результат не изменился, пользователь видит обычное подтверждение; если изменился, видит новый курс и итог и явно принимает их без дополнительного второго окна.
12. Оркестратор создаёт заявку с последними подтверждёнными условиями и связывает её с ключом операции.
13. В основном синхронном сценарии в одной атомарной бизнес-операции списывается исходная сумма, зачисляется целевая сумма и заявка становится `completed`.
14. Пользователь видит результат `completed` с фактическими суммами.
15. Локальная история обновляется представлением заявки и согласованным состоянием балансов.

При необходимости дополнительной проверки вместо шага 13 выполняется обязательное предупреждение, атомарное резервирование и переход `created → pending`; дальнейшее завершение описано в разделах 8, 11 и 12.

**Связанные требования:** `UR-001`–`UR-013`, `FR-004`–`FR-029`, `VAL-001`–`VAL-015`.

## 7. Компоненты системы

Логический компонент не обязан быть отдельным deployable-сервисом. Компоненты обозначают границы ответственности, а не технологический стек.

| Компонент | Назначение и ответственность | Входные данные | Результат | Взаимодействия / зависимости | Ограничения и что не входит в ответственность |
|---|---|---|---|---|---|
| Представление обмена и истории | показывает форму, балансы, подтверждения, результаты и локальную историю; блокирует повторное действие | системное состояние, котировка, балансы, заявки истории | пользовательское действие и отображённое состояние | контроллер потока, локальная история | не выполняет финансовый расчёт и не хранит финансовую истину |
| Контроллер пользовательского потока | координирует состояния формы, подтверждение курса, переход к результату и возврат после ошибки | действия пользователя и результаты остальных компонентов | согласованное состояние для представления | котировки, расчёт/валидация, оркестратор заявки | не определяет визуальные токены и окончательные API-контракты |
| Компонент котировок | вызывает CoinGecko, проверяет и нормализует ответ, создаёт ID котировки | запрос цены Tether в RUB и времени источника | корректная котировка либо ошибка курса | CoinGecko, контроллер потока | не создаёт собственный market data, не прогнозирует курс |
| Компонент расчёта и валидации | применяет формулы, округление и проверки суммы/пары/минимума | сумма, пара, котировка, доступный баланс | предварительный или подтверждаемый результат, ошибки валидации | компонент котировок, компонент баланса | не изменяет баланс и статус заявки |
| Оркестратор заявки | создаёт заявку, выбирает sync/async, обеспечивает допустимые переходы и идемпотентный результат | подтверждённые условия, ключ операции, актуальный баланс | заявка и её текущее/терминальное состояние | баланс/резерв, шлюз проверки, демо-хранилище | не реализует внутренние правила дополнительной проверки |
| Компонент баланса и резерва | проверяет актуальность, изменяет два баланса, создаёт/списывает/освобождает резерв | кошелёк, валюты, суммы, ожидаемый признак актуальности, ID заявки | согласованное состояние балансов или контролируемая ошибка | источник баланса, оркестратор, демо-хранилище | не вычисляет рыночный курс и не решает судьбу заявки самостоятельно |
| Шлюз дополнительной проверки | передаёт подтверждённую заявку и принимает итог | заявка `pending` и подтверждённые условия | `completed` с фактическими значениями либо `rejected` | внешняя дополнительная проверка, оркестратор | причины и алгоритмы проверки остаются внешними |
| Демонстрационное хранилище | сохраняет балансы, заявки, резерв, ключи попыток и историю | атомарный результат бизнес-операции | восстановимое локальное состояние | оркестратор, баланс/резерв, представление истории | не является production-хранилищем финансовых данных |

**Связанные требования:** `FR-004`–`FR-036`, `DR-001`–`DR-020`, `NFR-001`–`NFR-004`, `CON-007`–`CON-009`.

## 8. Последовательность взаимодействий

### 8.1. Синхронный успешный поток

После загрузки формы UI получает котировку и балансы, рассчитывает предварительный результат, при отправке повторно проверяет курс и баланс, получает подтверждение пользователя и передаёт оркестратору ключ операции. Оркестратор в одной бизнес-транзакции регистрирует заявку, списывает исходный баланс, зачисляет целевой, переводит заявку в `completed`, фиксирует результат идемпотентности и обновляет историю.

Диаграмма: [`diagrams/sequence-sync.mmd`](diagrams/sequence-sync.mmd).

### 8.2. Поток с изменившимся отображаемым результатом

Повторная котировка создаёт новый расчёт. Сравниваются не скрытые знаки курса, а отображаемые получаемые суммы после одинакового округления. При различии обычное подтверждение заменяется представлением нового курса и итога. После согласия именно новая котировка становится подтверждённой; повторное дополнительное подтверждение не показывается.

### 8.3. Асинхронный поток `pending → completed`

До перехода в async пользователь получает предупреждение о возможном изменении курса и результата. Создание заявки, резервирование исходной суммы, переход в `pending`, сохранение ключа операции и обновление истории образуют одну атомарную бизнес-операцию. Внешняя проверка позднее возвращает фактический курс и сумму. Завершение атомарно списывает резерв, зачисляет фактическую целевую сумму, фиксирует фактические условия и переводит заявку в `completed`.

### 8.4. Асинхронный поток `pending → rejected`

Начало аналогично предыдущему потоку. При отклонении резерв освобождается, целевой баланс не увеличивается, заявка становится `rejected`, история обновляется. Причина отклонения не обязательна в первой версии.

Диаграмма async-потоков: [`diagrams/sequence-async.mmd`](diagrams/sequence-async.mmd).

### 8.5. Недостаточный баланс

Если при вводе сумма выше доступного остатка, отправка блокируется. Если баланс изменился перед созданием заявки, модуль обновляет отображение: при достаточности продолжает, при недостаточности не создаёт заявку и возвращает понятную ошибку с актуальным доступным остатком.

### 8.6. Недоступность курса

Без корректной повторной котировки заявка не создаётся. Пользователь получает сообщение о невозможности получить курс и возвращается к основному экрану; неизвестные условия не фиксируются.

### 8.7. Повтор пользовательского запроса

Повтор с тем же ключом операции не запускает обработку заново. Если первая попытка ещё выполняется, возвращается её текущее состояние; если завершена — сохранённый результат. Баланс, резерв и история не применяются повторно.

**Связанные требования:** `FR-008`–`FR-012`, `FR-016`–`FR-028`, `FR-035`, `FR-036`, `ERR-003`–`ERR-009`, `NFR-001`.

<a id="sdd-10"></a>
## 10. Работа с курсом

Согласованный запрос получает цену `tether` в `rub` и время последнего обновления источника. Успешный ответ должен содержать конечное положительное числовое значение и корректное время источника. Отсутствие RUB, неполный ответ, тайм-аут, недоступность, неположительное/некорректное значение или непригодное время трактуются как ошибка курса.

После нормализации модуль создаёт уникальный идентификатор котировки и сохраняет:

- цену 1 USDT в RUB;
- время обновления источника;
- время получения модулем;
- рассматриваемую пару и назначение снимка.

Формулы:

- RUB → USDT: `sourceAmountRUB / rateRUBPerUSDT`;
- USDT → RUB: `sourceAmountUSDT * rateRUBPerUSDT`.

Отображаемая сумма округляется до одного знака после точки. Комиссия и спред равны нулю и не моделируются отдельными слагаемыми.

Перед созданием заявки обязательны новый запрос и новый расчёт. Для определения необходимости повторного согласия сравниваются отображаемые результаты после одинакового округления. Изменение скрытых знаков курса без изменения отображаемой суммы не требует повторного согласия. Отдельный таймер срока действия пользователю не показывается.

В sync-потоке подтверждённый курс является фактическим. В async-потоке заявка хранит подтверждённые значения, а при `completed` дополнительно получает фактический курс и фактическую сумму.

Ошибка курса до создания заявки не должна создавать заявку с неизвестными условиями и не должна изменять баланс.

**Связанные требования:** `FR-004`–`FR-014`, `BRL-004`, `BRL-005`, `BRL-008`–`BRL-010`, `VAL-010`–`VAL-013`, `ERR-004`–`ERR-006`.

<a id="sdd-11"></a>
## 11. Проверка и изменение баланса

Для каждой валюты различаются:

- общий остаток;
- активный резерв;
- доступный остаток = общий остаток − сумма активных резервов.

При вводе используется последнее полученное состояние. Перед созданием заявки модуль повторно получает баланс и логический признак актуальности. Конкретное имя версии не фиксируется; требуется возможность обнаружить конкурентное изменение между проверкой и применением.

«Обменять всё» подставляет доступный, а не общий остаток исходной валюты. Если актуальный баланс изменился, но остаётся достаточным, представление обновляет значения и операция продолжается. При недостаточности заявка не создаётся.

Атомарные бизнес-операции:

1. **Sync completion:** регистрация ключа и заявки, списание исходной суммы, зачисление целевой суммы, `completed`, время завершения и история применяются как единое целое.
2. **Enter pending:** регистрация ключа и заявки, создание одного резерва, `pending` и история применяются как единое целое.
3. **Async completion:** активный резерв списывается один раз, целевой баланс увеличивается на фактическую сумму, фактические условия фиксируются, заявка становится `completed`.
4. **Async rejection:** активный резерв освобождается один раз, заявка становится `rejected`, целевой баланс не изменяется.

Если резервирование не удалось после устойчивого создания заявки, заявка завершается `rejected`; активный резерв отсутствует, балансы не меняются. Валидационные, курсовые и балансовые ошибки до создания заявки не создают заявку.

Любая повторная доставка операции или события должна распознаваться по ключу попытки, состоянию заявки и связи с резервом так, чтобы повторное списание, зачисление, освобождение или потребление резерва было невозможно.

**Связанные требования:** `FR-015`–`FR-028`, `BRL-002`, `DR-018`, `DR-019`, `VAL-006`, `VAL-012`, `ERR-003`, `ERR-007`–`ERR-009`, `NFR-001`.

## 12. Жизненный цикл заявки

Диаграмма: [`diagrams/state-machine.mmd`](diagrams/state-machine.mmd).

| Текущее состояние | Триггер | Следующее состояние | Действия при входе | Действия с балансом | Действия с резервом | Пользовательский результат |
|---|---|---|---|---|---|---|
| — | подтверждённые условия и успешная регистрация | `created` | фиксируются ID, ключ и подтверждённые условия | финансовое изменение ещё не считается применённым | отсутствует | обработка |
| `created` | успешное sync-выполнение | `completed` | фиксируются фактические значения и время завершения | исходный баланс уменьшается, целевой увеличивается | не создаётся | успех |
| `created` | sync-отклонение или ошибка после создания | `rejected` | фиксируются терминальный статус и время | финансового изменения нет | отсутствует | обмен не выполнен |
| `created` | дополнительная проверка принята и резерв создан | `pending` | фиксируются статус, резерв и история | общий баланс не списывается; доступный уменьшается | создаётся один активный резерв | ожидание, сумма в резерве |
| `pending` | успешное async-завершение | `completed` | фиксируются фактический курс, сумма и время | целевой баланс увеличивается на фактическую сумму | резерв списывается один раз | фактический результат |
| `pending` | async-отклонение | `rejected` | фиксируются терминальный статус и время | целевой баланс не изменяется; доступный восстанавливается | резерв освобождается один раз | обмен не выполнен, резерв снят |

Недопустимые переходы:

- из `completed` или `rejected` в любое другое состояние;
- `pending → created`;
- `created → pending` без успешного резервирования;
- любое состояние `cancelled` или `expired`;
- наличие активного резерва у `created`, `completed` или `rejected`.

Повторное событие завершения возвращает сохранённый результат и не меняет баланс или резерв. История обновляется после каждого принятого перехода. Заявка не должна оставаться в `created` после неуспешной обработки, начатой после её устойчивого создания.

**Связанные требования:** `FR-023`–`FR-027`, `BRL-011`–`BRL-017`, `DR-011`–`DR-015`, `ERR-007`–`ERR-009`.

<a id="sdd-14"></a>
## 14. Нефункциональные аспекты высокого уровня

### 14.1. Идемпотентность и непротиворечивость

- ключ операции создаётся на пользовательскую попытку, но окончательное имя заголовка или поля не фиксируется;
- повтор возвращает результат первой обработки;
- состояние заявки и финансовые действия защищаются от повторного применения;
- конкурентное изменение баланса обнаруживается логическим признаком актуальности;
- атомарные границы раздела 11 не допускают частичного обмена.

### 14.2. Бизнес-инварианты

1. Одна пользовательская попытка создаёт не более одной заявки.
2. Одна попытка вызывает не более одного финансового изменения.
3. Доступный баланс не может стать отрицательным.
4. Активный резерв связан только с заявкой `pending`.
5. Один резерв не может быть одновременно списан и освобождён.
6. Терминальная заявка не возвращается в `created` или `pending`.
7. `completed` отражает согласованное изменение обоих валютных балансов.
8. `rejected` не зачисляет целевую валюту.
9. Повторное событие завершения не изменяет баланс повторно.
10. Заявка хранит условия, подтверждённые пользователем.
11. Асинхронный результат хранит фактические условия выполнения.
12. При недостаточном доступном балансе заявка не создаётся.
13. Неподдерживаемая пара отклоняется независимо от UI.
14. Ошибка внешнего курса не создаёт заявку с неизвестными условиями.

### 14.3. Остальные ограничения

- локальная история сохраняется между перезагрузками одного браузера;
- недоступность CoinGecko приводит к контролируемой ошибке, а не к использованию неизвестного курса;
- будущие UX, Gherkin и OpenAPI обязаны использовать те же формулы, статусы, округление и границы;
- внутренние технические детали не раскрываются пользователю;
- численные SLA, RPS, latency и availability не задаются без источника.

**Связанные требования:** `NFR-001`–`NFR-004`, `FR-020`–`FR-022`, `VAL-014`, `CON-007`.

## 15. Допущения, решения и открытые вопросы

### 15.1. Согласованные решения этапа 1

Действуют `DEC-001`–`DEC-035`: граница до терминального результата, две валюты и пары, правила суммы/курса/баланса, четыре статуса, резерв, идемпотентность, локальная история, клиентская симуляция, отсутствие отмены/уведомлений/комиссии и разделение подтверждённых и фактических async-значений.

### 15.2. Активные допущения

- `AS-001`: группировка больших чисел через пробел;
- `AS-002`: время в локальном часовом поясе браузера с возможным UTC-смещением;
- `AS-004`: минимальный набор UX-состояний;
- `AS-005`: точные визуальные параметры определяет UX-этап.

`AS-003` заменено проектным решением `DEC-036`.

### 15.3. Проектные решения этапа 2

| ID | Решение | Классификация |
|---|---|---|
| `DEC-036` | в демонстрационном режиме `pending` вызывается явным переключателем «Дополнительная проверка» вне production-поведения; перед отправкой пользователь всё равно получает обязательное предупреждение | проектное решение этапа 2 |
| `DEC-037` | выделенные компоненты являются логическими границами и не предписывают микросервисы или deployable-единицы | проектное решение этапа 2 |
| `DEC-038` | sync completion, вход в `pending`, async completion и async rejection имеют отдельные атомарные бизнес-границы из раздела 11 | проектное решение этапа 2 |
| `DEC-039` | повторная проверка баланса использует версию или эквивалентный логический признак актуальности без фиксации имени API-поля | проектное решение этапа 2 |
| `DEC-040` | повторные события завершения подавляются сочетанием терминального состояния, связи с заявкой/резервом и идемпотентной записи результата | проектное решение этапа 2 |

### 15.4. Анализ вариантов демонстрационного `pending`

| Вариант | Понятность для демонстрации | Влияние на UX | Риск смешения с production | Удобство Gherkin | Удобство клиентской реализации |
|---|---|---|---|---|---|
| специальная сумма | средняя | незаметное скрытое правило | высокий | удобно, но семантически ложно | очень простое |
| явный demo-переключатель | высокая | дополнительный элемент только demo-mode | низкий | максимально прозрачно | простое |
| детерминированное правило по ключу/счётчику | низкая для демонстратора | UI не меняется | средний | воспроизводимо, но хуже читается | среднее |

Рекомендуется явный demo-переключатель. Он не изображает реальное AML/KYC/fraud-правило, легко отключается вне демонстрации и однозначно передаётся в Gherkin.

### 15.5. Открытые вопросы

Остаются только `MEDIUM`:

- `OQ-M-01` — окончательный формат группировки больших чисел;
- `OQ-M-02` — окончательный часовой пояс истории и `pending`;
- `OQ-M-04` — окончательный демонстрационный набор UX-состояний.

`OQ-M-03` закрыт решением `DEC-036`. Новых `BLOCKER` или `HIGH` не выявлено.

**Связанные требования:** `FR-031`, `ERR-012`, `UX-007`, `NFR-001`, `CON-007`, `CON-008`.

## 16. Связи с UX, Gherkin и OpenAPI

### 16.1. Передача в UX/UI

| Пользовательское состояние | Обязательные данные | Доступные действия | Системная причина блокировки / перехода | Связанное состояние заявки |
|---|---|---|---|---|
| default | обе валюты, общий/зарезервированный/доступный баланс, курс и время, поля суммы | выбор пары, ввод, «Обменять всё» | нет котировки или блокирующая валидация | заявки ещё нет |
| validation error | введённое значение, конкретная понятная ошибка, актуальный баланс/минимум | исправить значение | формат, минимум, баланс или пара | заявки ещё нет |
| normal confirmation | исходная и получаемая суммы, валюты, подтверждаемый курс | подтвердить или вернуться | после подтверждения кнопка блокируется | до `created` |
| changed result | новый курс, новый итог, неизменная исходная сумма | согласиться или вернуться | требуется согласие с последним отображаемым результатом | до `created` |
| pending | подтверждённые условия, резерв, предупреждение о возможном изменении, время | перейти к истории/основному экрану | повторное подтверждение недоступно | `pending` |
| completed | фактические исходная и полученная суммы, курс, время | основной экран/история | терминальное состояние | `completed` |
| rejected | обмен не выполнен, резерв освобождён при наличии | основной экран/история | терминальное состояние | `rejected` |
| technical error | понятный текст, при необходимости код | возврат на основной экран | неизвестные или небезопасные условия | нет заявки либо согласованное текущее состояние |
| mobile default | тот же системный набор данных, что и desktop default | те же бизнес-действия | те же системные ограничения | заявки ещё нет |

Резерв должен быть явно отличим от доступного остатка. Визуальные токены, размеры и компоненты интерфейса не определяются SDD.

### 16.2. Передача в Gherkin

| Группа сценариев | Предусловия / вход | Ожидаемые проверки |
|---|---|---|
| Sync Happy Path | корректная пара, сумма, котировка, достаточный баланс | `created → completed`, одно списание, одно зачисление, история обновлена |
| Изменившийся результат | повторная котировка меняет отображаемую сумму | показан новый итог; заявка создаётся только после согласия; второго окна нет |
| Недостаточный баланс | сумма выше доступного либо баланс стал недостаточным перед отправкой | заявка не создана, баланс не изменён, показан актуальный остаток |
| Баланс изменился, но достаточен | версия баланса изменилась, средств хватает | отображение обновлено, текущая попытка может продолжиться |
| CoinGecko unavailable/invalid | тайм-аут, отсутствие RUB, некорректная цена/время | заявка не создана, финансового эффекта нет, понятная ошибка |
| Идемпотентный повтор | тот же ключ операции доставлен повторно | не более одной заявки и одного финансового изменения; возвращается первый результат |
| `pending → completed` | demo-переключатель, успешная внешняя проверка | резерв создан и списан один раз; фактические значения сохранены и показаны |
| `pending → rejected` | demo-переключатель, отклонение проверки | резерв освобождён, целевого зачисления нет, история содержит `rejected` |
| Ошибка резервирования | async выбран, резерв создать нельзя | заявка после создания становится `rejected`, баланс не меняется |
| Неподдерживаемая пара | системный запрос обходит ограничения UI | заявка отклонена до финансового эффекта |

`.feature` на этапе 2 не создаётся.

### 16.3. Передача в OpenAPI

| Будущая логическая операция | Логические входы | Логический результат | Ошибки / ограничения, которые должны быть отражены |
|---|---|---|---|
| Получить контекст формы | кошелёк/пользовательский контекст | балансы RUB/USDT и признак актуальности | недоступность источника баланса |
| Получить котировку | разрешённая пара или запрос цены Tether в RUB | ID котировки, курс, время источника | недоступность, тайм-аут, неполный/некорректный ответ |
| Создать подтверждённую попытку обмена | пара, исходная сумма, подтверждённая котировка и результат, ключ операции, признак актуальности баланса | заявка `completed`, `pending` или `rejected` с подтверждёнными значениями | валидация, недостаточный/изменившийся баланс, повтор ключа, ошибка резервирования, техническая ошибка |
| Получить состояние заявки | идентификатор заявки и контекст кошелька | текущий статус, резерв, подтверждённые и фактические значения | заявка недоступна в данном контексте |
| Получить локальную историю, если контракт потребуется прототипу | контекст демонстрационного кошелька | записи направления, сумм, статуса и времени | локальный характер и отсутствие межустройственной синхронизации |
| Принять результат дополнительной проверки как внутреннее взаимодействие | ID заявки, терминальный результат, фактический курс и сумма при успехе, идентификатор события/результата | идемпотентно применённое терминальное состояние | повтор события, недопустимый переход, отсутствие активного резерва |

Окончательные REST-пути, имена полей и HTTP-коды не фиксируются. OpenAPI JSON на этапе 2 не создаётся.

**Связанные требования:** `UR-001`–`UR-016`, `UX-001`–`UX-020`, `ART-002`–`ART-008`, `NFR-004`.
